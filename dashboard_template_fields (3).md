# Описание и инструкция по заполнению дашборда автономного анализа проекта

## Назначение файлов

`dashboard_template.html` — готовый автономный HTML-шаблон. В нём уже находятся дизайн, расчёты и логика отображения. Модель должна сформировать только объект данных и поставить его вместо маркера:

```html
/*__DATA__*/
```

Не изменяй CSS, HTML-разметку и JavaScript шаблона. Не добавляй внешние библиотеки, ссылки или новые скрипты.

## Что представляет собой шаблон

Шаблон формирует одностраничный управленческий дашборд по результатам автономного анализа проекта. Его задача — показать не техническое состояние разработки, а готовность проекта с точки зрения клиентской ценности и прохождения клиентского пути.

Дашборд отвечает на пять вопросов:

1. Какой клиентский путь меняет проект и для кого он создаётся?
2. Как должен измениться опыт клиента в формате «было → стало»?
3. Насколько проект в целом готов по оценке модели?
4. Какие этапы клиентского пути уже реализованы, находятся в работе, только запланированы или заблокированы?
5. Какие риски критичны и что нужно сделать в первую очередь?

Шаблон является автономным: все данные, стили и логика находятся внутри одного HTML-файла. После подстановки JSON файл можно открыть локально в браузере без сервера и подключения к интернету.

## Заполняемые панели дашборда

| Панель | Где находится | Какие поля использует | Для чего нужна |
| --- | --- | --- | --- |
| Описание проекта | Левая часть верхней панели | `meta.client_path_name`, `meta.project_name`, `meta.client`, `meta.before`, `meta.after` | Задаёт контекст анализа: клиентский путь, название инициативы, целевой клиент и наблюдаемое изменение его опыта. Надпись «Автономный анализ проекта» является частью интерфейса и не заполняется. |
| Общая готовность | Верхняя карточка справа | `readiness` | Показывает самостоятельную итоговую оценку модели в процентах. Значение не вычисляется из среднего по этапам. |
| Оценка ИИ по клиентскому пути | Нижняя карточка справа | `meta.decision`, `summary.conclusion` | Показывает вердикт `GO`, `PIVOT` или `NO GO` и постоянный текст общего вывода модели. Карточка не открывается по клику. |
| Клиентский путь | Центральная часть | `items` | Дословно воспроизводит все этапы и буллиты из «образа результата». Количество и порядок этапов динамические; серыми остаются элементы, не относящиеся к анализируемой инициативе. |
| Риски | Нижняя левая панель | `summary.risks` | Фиксирует ключевые обстоятельства, которые могут помешать достижению клиентского результата или следующему шагу проекта. |
| Что важно делать | Нижняя правая панель | `summary.priorities` | Показывает ближайшие приоритетные действия в порядке важности. |

Панелей ресурсов, эффективности и отдельной панели «Общий вывод» в текущей версии нет. Общий вывод встроен в карточку оценки ИИ под меткой вердикта.

## Что заполняет модель, а что делает шаблон

Модель самостоятельно формирует:

- содержание всех полей `meta`, кроме необязательной даты;
- общую готовность проекта `readiness`;
- решение `GO`, `PIVOT` или `NO GO`;
- общий вывод;
- точную копию этапов и буллитов клиентского пути из «образа результата»;
- признак применимости и статус только для тех этапов и буллитов, которые относятся к рассматриваемой инициативе;
- риски и приоритетные действия.

Шаблон автоматически:

- отображает общую готовность в круговом индикаторе;
- задаёт цвет метки вердикта;
- рассчитывает готовность каждого этапа по его применимым критериям;
- исключает неприменимые этапы и критерии из расчёта;
- окрашивает этапы и отметки критериев по статусам;
- адаптирует расположение панелей под размер экрана.

## Общая структура данных

```json
{
  "meta": {
    "client_path_name": "Название клиентского пути",
    "project_name": "Название проекта",
    "client": "Кто является клиентом и кому должно стать лучше",
    "before": "Как клиент решает задачу сейчас",
    "after": "Как клиент должен решать задачу после реализации проекта",
    "decision": "GO",
    "generated_at": "2026-09-02T12:00:00Z"
  },
  "readiness": 72,
  "items": [],
  "summary": {
    "conclusion": "Общий вывод модели",
    "risks": [],
    "priorities": []
  }
}
```

## Поля `meta`

| Поле | Где показывается | Смысл и правила заполнения |
| --- | --- | --- |
| `client_path_name` | Главный крупный заголовок | Название анализируемого клиентского пути. Это путь или задача клиента, а не название продукта. Пример: «Подготовка руководителя к управленческой встрече». |
| `project_name` | Подзаголовок под главным заголовком | Название проекта, продукта или инициативы. |
| `client` | Цветной блок «Клиент» | Кто получает основную пользу от проекта и кому должно стать лучше. Нужна конкретная роль или группа и её задача. |
| `before` | Первая часть блока «Было → стало» | Текущее состояние клиентского пути: как человек действует сейчас и в чём его сложность. |
| `after` | Вторая часть блока «Было → стало» | Целевое состояние: как изменится опыт клиента и какой результат он получит. Формулируй наблюдаемое изменение, а не список функций продукта. |
| `decision` | Метка в карточке «Оценка ИИ по клиентскому пути» под кругом готовности | Экспертное решение модели: `GO`, `PIVOT` или `NO GO`. Под меткой постоянно отображается текст из `summary.conclusion`; метка не является кнопкой. |
| `generated_at` | Дата обновления внизу страницы | Дата и время формирования анализа. Рекомендуемый формат — ISO 8601. Поле необязательно. |

### Смысл решения

- `GO` — текущий подход можно продолжать: ключевые основания подтверждены, критических блокеров нет.
- `PIVOT` — ценность проекта сохраняется, но подход, объём или клиентский путь нужно существенно скорректировать.
- `NO GO` — продолжение проекта в текущем виде не обосновано или заблокировано критическими ограничениями.

Цвет метки задаётся шаблоном автоматически: `GO` — зелёный, `PIVOT` — жёлтый, `NO GO` — красный. Если поле всё же пропущено, шаблон технически подставит решение по проценту готовности, но модель не должна полагаться на этот резервный механизм.

## Поле `readiness`: общая готовность проекта

`readiness` — обязательная экспертная оценка модели от `0` до `100`. Она показывается в большом круговом индикаторе.

Модель оценивает общую готовность проекта самостоятельно и целостно. Это не среднее арифметическое готовности этапов или буллетов. При оценке нужно учитывать:

- подтверждённость клиентской ценности и образа результата;
- зрелость применимых этапов клиентского пути;
- критичность незакрытых критериев;
- риски, зависимости и блокеры;
- возможность безопасно перейти к следующему шагу проекта.

Примеры: `0` — проект фактически не готов; `54` — готовность 54%; `100` — проект полностью готов в рамках выбранного горизонта оценки. Для совместимости шаблон также принимает дробь от `0` до `1`, но модели следует передавать целое число от `0` до `100`.

## Поле `items`: этапы клиентского пути

`items` — массив этапов клиентского пути. Единственным источником для него является предоставленный «образ результата».

### Критическое правило: копировать дословно

Модель обязана перенести из «образа результата»:

- все этапы без исключений;
- названия этапов без переформулирования;
- все буллиты каждого этапа без сокращений, дополнений и смысловой редакции;
- исходный порядок этапов и буллитов.

Нельзя адаптировать формулировки под рассматриваемый проект, объединять похожие пункты, удалять «неактуальные» этапы или добавлять новые. Даже если этап или буллит не относится к инициативе, он всё равно должен присутствовать в `items` и отображаться серым.

Сначала скопируй весь клиентский путь, затем отдельно оцени применимость каждого этапа и каждого буллита к рассматриваемой инициативе.

Структура этапа:

```json
{
  "title": "Название этапа",
  "description": "Что происходит с клиентом на этом этапе",
  "applicable": true,
  "assessment": [
    {
      "text": "Критерий готовности этапа",
      "status": "done",
      "applicable": true
    }
  ]
}
```

| Поле | Обязательность | Смысл и правила заполнения |
| --- | --- | --- |
| `title` | Обязательно | Дословное название этапа из «образа результата». Нельзя переформулировать. |
| `description` | Обязательно | Описание этапа из «образа результата», если оно там есть. Не дополняй его техническими деталями проекта. |
| `applicable` | Обязательно только для относящегося этапа | Передай `true`, только если этап относится к рассматриваемой инициативе. Если поле отсутствует или имеет любое другое значение, этап по умолчанию серый и не участвует в расчёте. |
| `assessment` | Обязательно | Полный массив буллитов этапа из «образа результата». Передавай все пункты в исходном порядке; шаблон больше не ограничивает их количество. |

Не передавай процент или цвет этапа вручную. Для относящегося этапа укажи `applicable: true`; шаблон рассчитает его готовность и цвет только по относящимся буллитам. Если к инициативе не относится ни один буллит, этап останется серым.

## Поля критерия `assessment`

| Поле | Обязательность | Смысл и правила заполнения |
| --- | --- | --- |
| `text` | Обязательно | Дословный текст буллита из «образа результата». Нельзя переформулировать, сокращать или дополнять. |
| `status` | Обязательно для применимого критерия | Текущее состояние: `done`, `partial`, `planned` или `blocked`. |
| `applicable` | Обязательно только для относящегося буллита | Передай `true`, только если буллит относится к рассматриваемой инициативе. Если поле отсутствует или имеет любое другое значение, буллит по умолчанию серый, его `status` игнорируется, а сам пункт исключается из расчёта. |

Для буллита, не относящегося к инициативе, достаточно передать только поле `text`. Не назначай ему статус искусственно. Модель задаёт `applicable` и `status`, а шаблон сам переводит их в визуальный цвет и учитывает в готовности этапа.

### Значения `status`

| Значение | Отметка и цвет | Вес в расчёте | Когда использовать |
| --- | --- | ---: | --- |
| `done` | Бирюзовый, реализовано | 1 | Критерий подтверждён материалами проекта и не требует существенной доработки. |
| `partial` | Фиолетовый, в работе | 0,5 | Результат уже создаётся или частично реализован, но остаётся значимый разрыв. |
| `planned` | Серый контур, запланировано | 0 | Результат ещё не реализован, но предусмотрен планом проекта. |
| `blocked` | Красный, блокирующий фактор | 0 | Отсутствующий результат блокирует следующий этап, пилот или достижение клиентского эффекта. Используй только для конкретного критического препятствия. |

Комментарии и пояснения к критериям в интерфейсе больше не показываются. Не передавай поля `comment`, `note` и `details`.

## Как определяется готовность

Готовность этапа:

```text
сумма весов применимых критериев / количество применимых критериев × 100%
```

Эта формула используется только для готовности отдельного этапа. В расчёт включаются исключительно буллиты с явным `applicable: true`. Все остальные пункты остаются серыми, исключаются из знаменателя и не снижают процент этапа.

Цвет применимого этапа:

- от 80% — зелёный;
- от 40% до 79% — жёлтый;
- ниже 40% — красный;
- этап без буллитов с явным `applicable: true` — серо-фиолетовый.

Общую готовность шаблон не вычисляет. Модель обязана передать её в поле верхнего уровня `readiness`. Значение может отличаться от среднего по этапам, поскольку модель учитывает критичность отдельных разрывов и общую доказательность материалов.

## Поле `summary`

| Поле | Где показывается | Смысл и правила заполнения |
| --- | --- | --- |
| `conclusion` | Постоянный текст оценки модели под меткой GO/PIVOT/NO GO | Цельный итог анализа: почему выбрано это решение, что уже подтверждено, что мешает проекту и можно ли переходить к следующему шагу. Не дублируй списки рисков и действий дословно. |
| `risks` | Панель «Риски» | Массив кратких ключевых рисков проекта. Каждый пункт должен описывать риск и его возможное последствие. |
| `priorities` | Панель «Что важно делать» | Массив ближайших действий, которые сильнее всего продвинут проект или снимут критические риски. Располагай по приоритету. |

После клиентского пути выводятся только две постоянные панели: «Риски» и «Что важно делать». Рекомендуется передавать от двух до пяти пунктов в каждом массиве.

## Требования к генерации итогового файла

1. Самостоятельно оцени общую готовность проекта и сформируй валидный JSON-объект по описанной структуре.
2. Замени в `dashboard_template.html` только маркер `/*__DATA__*/` на объект целиком, без Markdown-ограждений и без дополнительного присваивания.
3. Не оставляй маркер в итоговом файле.
4. Не меняй остальную часть HTML.
5. Сохрани результат как отдельный `.html`-файл.

В итоговом HTML строка должна выглядеть так:

```html
<script>window.__DATA__ = { ...готовый объект... };</script>
```

## Устаревшие поля

Не генерируй следующие поля из прежних версий шаблона: `pct`, `color`, `label`, `comment`, `note`, `details`, `resources`, `summary.efficiency`. Они не используются текущим интерфейсом или рассчитываются автоматически. Поле этапа `description` и поле `summary.conclusion`, напротив, используются и обязательны для заполнения.
