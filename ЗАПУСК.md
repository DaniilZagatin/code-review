# PKO progress — как запустить

Инструмент берёт **образ результата инициативы** (этапы и буллиты текстом) и
**код** (репозиторий по SSH или ZIP-архив), проверяет каждый буллит по коду и
выпускает HTML-отчёт о готовности с решением GO / PIVOT.

Работать можно двумя способами: через веб-интерфейс (`pko serve` + Next.js) или
одной командой из терминала (`pko progress`). Дальше — по шагам.

---

## 1. Что нужно поставить заранее

| Что | Версия | Проверить |
|---|---|---|
| Python | 3.11 и выше | `python --version` |
| Node.js | 20 и выше | `node --version` |
| Git | любой свежий | `git --version` |

Отлаживалось на Python 3.14 и Node 24 под Windows 11. На macOS и Linux
запускается так же, отличается только активация виртуального окружения.

Под Windows команды ниже удобнее выполнять в **Git Bash** — он ставится вместе
с Git. В PowerShell тоже работает, отличия отмечены отдельно.

---

## 2. Распаковать и поставить бэкенд

```bash
cd pko-progress          # каталог, куда распаковали архив
python -m venv .venv
source .venv/bin/activate         # Windows PowerShell: .venv\Scripts\Activate.ps1
pip install -e .
```

`pip install -e .` ставит пакет вместе с зависимостями (fastapi, uvicorn,
openai, httpx) и добавляет команду `pko`. Проверить:

```bash
pko --version
```

## 3. Проверить, что всё собралось

Тесты не ходят в сеть и не обращаются к модели — их можно прогнать сразу:

```bash
python tests/run_tests.py
```

Ожидается **302 теста, 301 прошло, 0 провалено, 1 пропущено**. Отчёт о прогоне
ляжет в `reports/TESTS.txt`.

При первом запуске тесты сами создадут тестовый репозиторий в
`tests/fixtures/mini_repo` — для этого нужен `git` в PATH.

## 4. Собрать фронтенды

Их два, и нужны они для разного.

**`frontend-app`** — обязателен, если пользуетесь командой `pko progress`: из
его сборки берётся часть HTML-отчёта. Без неё команда упадёт с ошибкой
«Дашборд-путь не собран».

```bash
cd frontend-app
npm ci
npm run build
cd ..
```

**`frontend-web`** — веб-интерфейс. Нужен, только если работаете через браузер.

```bash
cd frontend-web
npm ci
npm run build      # для разработки достаточно npm run dev, см. шаг 6
cd ..
```

`npm ci` ставит версии из `package-lock.json` — они в архиве есть, поэтому у
вас соберётся ровно то же, что собиралось у нас. `npm install` тоже сработает,
но может подтянуть более свежие версии.

## 5. Настроить доступ к модели

Агенту нужен OpenAI-совместимый эндпоинт (`/chat/completions`).

**По умолчанию** он берёт внутренний GLM-5.2 из `backend/pko/defaults.py` —
это работает только внутри корпоративной сети. Никаких настроек тогда не
требуется, шаг можно пропустить.

**Чтобы указать свой эндпоинт**, скопируйте `.env.example` в `.env` и
раскомментируйте три строки:

```bash
cp .env.example .env
```

```
PKO_ASSEMBLER_BASE_URL=https://<ваш-эндпоинт>/v1
PKO_ASSEMBLER_MODEL=<имя модели>
PKO_ASSEMBLER_API_KEY=<ключ>
```

`.env` подхватывается автоматически при запуске — `export` делать не нужно.
В архив он не входит и в git не попадает.

> **Для GLM-5.2 держите thinking выключенным.** С включённым режимом
> рассуждений модель съедает весь бюджет ответа и возвращает пустоту. В
> веб-форме это галочка «thinking», в CLI — флаг `--thinking`; по умолчанию
> выключено, так и оставьте.

## 6. Запуск: веб-интерфейс

Два процесса в двух терминалах.

Терминал 1 — бэкенд:

```bash
source .venv/bin/activate
pko serve --port 8000
```

Терминал 2 — фронтенд:

```bash
cd frontend-web
npm run dev
```

Открыть **http://localhost:3000**. Фронтенд сам проксирует `/api` на
`http://127.0.0.1:8000`; если бэкенд поднят на другом порту, задайте
`PKO_BACKEND_URL` перед `npm run dev`.

В форме:

1. **Клиентский путь** — текст инициативы (формат в шаге 8).
2. **Репозиторий** — SSH-ссылка на Bitbucket и ветка. Доступ идёт через ваш
   `ssh-agent`, отдельных ключей инструмент не хранит. Поле можно оставить
   пустым и загрузить ZIP-архив с кодом.
3. **Описание инициативы** — необязательно; из него агент формулирует
   «AS IS / Now / To Be» в шапку отчёта.

Дальше видно живой прогресс, в конце — дашборд и кнопка «Скачать отчёт».

## 7. Запуск: командная строка

```bash
source .venv/bin/activate

# по локальному клону репозитория
pko progress --journey-file initiative.md --repo-path /path/to/repo

# по ZIP-архиву с кодом
pko progress --journey-file initiative.md --zip /path/to/code.zip

# по Bitbucket через SSH
pko progress --journey-file initiative.md \
  --url ssh://git@stash.example.ru:7999/project/repo.git --branch develop
```

Результат — в каталоге `pko-progress-out` (меняется флагом `--out`):

- `dashboard.html` — отчёт для чтения, самодостаточный файл;
- `progress_report.html` — расширенный отчёт;
- `progress_model.json` — все данные прогона, включая **все** ссылки на код,
  и подтверждённые, и отклонённые. Это след проверки: в отчёт отклонённые не
  выводятся, а здесь их видно.

Полезные флаги: `--max-steps` (бюджет шагов агента, по умолчанию 80),
`--quiet` (не печатать ход работы), `--no-fetch` (не обновлять зеркало
репозитория).

## 8. Формат ввода

Понимаются два формата, и выбирается он **по структуре текста**, а не по
шапке — руками ничего указывать не нужно.

**Ручной клиентский путь** — буллиты под каждым этапом:

```
Клиентский путь: Key Clients
Проект: Copilot сотрудника по расчёту моделей

## Подготовка к встрече
- Принимает от пользователя модель и запрос в текстовой форме
- Производит необходимые расчёты по модели

## Детальный анализ сделки
- Выполняет сценарный анализ модели
```

**Файл инициативы из колоды** — сначала все заголовки, потом все буллиты,
потом дословный хвост из презентации. Такой файл тоже разбирается правильно:
хвост в оценку не попадает.

Маркером буллита может быть `-`, `*`, `•`, `·`, `▪`, `●`, `‣`, `⁃`, `–`, `—`.
Заголовок этапа — `## Название` или `Этап 3. Название`.

**Проверить разбор до запуска анализа** (не ходит ни в сеть, ни в модель):

```bash
pko parse --journey-file initiative.md
```

Команда покажет опознанный формат, название пути, этапы и полный список
буллитов. Если буллитов оказалось больше, чем в документе, — в оценку затянут
лишний текст, и это видно до того, как потрачен прогон.

## 9. Как читать отчёт

**Две оценки в шапке.** Оценивается прототип, поэтому чисел два:

- **Прототип** — доказана ли идея. По нему считается решение: ≥40% — GO,
  иначе PIVOT.
- **Промышленное решение** — получает ли пользователь результат. Строже:
  ограничение считается дырой, а написанный, но не подключённый код для
  пользователя не существует.

Оба числа код считает сам по статусам буллитов, двумя наборами весов —
легенда с весами напечатана прямо в отчёте.

**Пять состояний буллита:** работает (100/100) · работает с ограничениями
(90/70) · код реализован, но не используется (70/30) · не работает,
реализовано частично (50/20) · не реализовано (0/0).

**Раскрытие пункта** — по клику, два буллита и шторка:

- **Проверка** — есть ли код и работает ли он, человеческим языком;
- **Как работает** — что система умеет и каким образом;
- **Ссылки на код** — закрытая шторка, внутри `файл:строка · имя` и фраза,
  что там происходит. Показываются **только подтверждённые** ссылки: путь и
  строка проверены по коду.

Внизу отчёта — замечания разбора: что не удалось подтвердить и где отчёт сам
себе не доверяет.

## 10. Если что-то не работает

**`pko: command not found`** — не активировано виртуальное окружение
(`source .venv/bin/activate`) или не выполнен `pip install -e .`.

**`Дашборд-путь не собран`** — не собран `frontend-app`, см. шаг 4.

**`Роль matcher не заведена` / `не настроена`** — не задан LLM-эндпоинт и
недоступен дефолтный. Заполните `.env`, см. шаг 5.

**Модель возвращает пустой ответ** — включён thinking. Выключите (см. шаг 5).

**Веб-страница выглядит несвёрстанной** — не пересобран `frontend-web` после
обновления. Выполните `npm run build` заново. Отдельно: файлы CSS проекта
обязаны сохраняться **без BOM** — BOM в `dashboard.css` ломает первый блок
правил, и вся страница едет.

**Тесты падают на создании фикстуры** — нет `git` в PATH или (под Windows) нет
`bash`. Поставьте Git и запускайте из Git Bash.

**Долгий первый прогон** — нормально: клонирование большого репозитория плюс
сессия агента могут занять до 15 минут. Повторный прогон того же коммита
берётся из кеша (`~/.pko/llm-cache`) и идёт почти мгновенно.

## 11. Чего в архиве нет и почему

- `node_modules/`, `.next/`, `__pycache__/`, `.venv/` — ставятся и собираются
  на месте командами выше.
- `.env` — там ключи; в архив он не кладётся никогда. Есть `.env.example`.
- `tests/fixtures/mini_repo/` — тестовый репозиторий, создаётся сам при первом
  прогоне тестов.
- `frontend-app/dist/` — сборка, делается командой из шага 4.
- Каталог `logs/` и служебные отчёты прошлых прогонов.

Сертификатов и ключей в архиве нет: проверено при сборке, ни одного файла
`.env`, `.pem`, `.key`, `.crt`, `.pfx` внутри не лежит.
